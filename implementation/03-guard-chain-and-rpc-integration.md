# 03. Guard Chain and RPC Integration

## Outcome

Implement the Guard CKB chain and local remote procedure call (RPC)/indexer path on the existing ECDSA threshold signature scheme (TSS) model with independent event validation, bounded custody construction, capacity and transaction verification, full-wrapper agreement identity, and script-group signing.

## Scope and Dependencies

- Read the [work breakdown](./README.md) and [integration contract](../README.md), then complete [work item 01](./01-shared-utils-codec-and-extractor.md) first. This work item may proceed in parallel with [work item 02](./02-watcher-ingest-path.md).
- Target repositories: [Utils](https://github.com/rosen-bridge/utils), [Guard Service](https://github.com/rosen-bridge/guard-service), and this integration tracker.
- Guard runtime registration order is not Rosen metadata wire order and must not be coupled to `SUPPORTED_CHAINS` positions.
- Canonical committed custody inputs with a constructor-only deep-first preference are accepted for the first mainnet CKB integration release (v1). Do not implement uncommitted-successor selection, wrapper-carried parent bytes, or package handling. The construction and no-fit choices are settled in the [decision register](../decisions-and-open-questions.md#accepted-decisions), while the README owns exact terminal handling; complete-read resource measurements and fee guardrails are deployment inputs.
- Preserve one Rosen input-lock group and one ECDSA TSS operation per constructed CKB transaction. The committed-only throughput rationale depends on the pinned Guard's configured bridge-wide ECDSA round limit, competing ECDSA load, and [work item 08's](./08-contract-deployment-handoff.md) measured provisioning of global untyped capacity and typed pools for each extensible user-defined token (xUDT). Keep that startup provisioning separate from H1's path-shape-derived target and cold service quanta in the [README](../README.md#custody-concurrency-and-transaction-chaining).
- Implement the selected constructor and CKB `agreementId` binding under Requirements. The two-node, live-indexer, and cycle measurements under Deployment validation lie outside this implementation pass and can revise policy or deployment values without blocking repository-local implementation.

## Requirements

### Package and Event Wiring

- Follow the Bridge Expansion Kit (RCS-003) Rosen Chain order: define the chain base and network interface, add the universal extractor, implement the chain, implement the RPC network, then wire the Guard service.
- Add `CkbRosenExtractor<string>` in Utils for serialized Guard transaction JSON. It must share work item 01's exact extra-witness envelope, selected-output binding, selected source-input OutPoint derivation, and normal-output semantics. This surface and focused Utils tests are mandatory, not an app-local substitute.
- Keep the universal extractor and Guard event verification free of input resolution. Guard fetches the canonical block by `sourceBlockId`, selects the unique transaction whose raw hash is `sourceTxId`, extracts the encoded selected output, and compares all event fields through the existing `verifyEvent` path. Do not call an unqualified raw-hash lookup a block-bound fetch. Derive the transaction index from that block only when needed and persist neither it nor `witness_hash` as another Rosen identity.
- Implement the event hook surface explicitly: either provide `verifyLockTransactionExtraConditions` for CKB or override `verifyEvent`. Choose the minimal option consistent with the canonical source-block and transaction-binding checks above, and do not leave the inherited default in place.
- Add Guard CKB and native-token registration, configuration, handlers, and service wiring without deriving runtime order from the extractor wire index. RCS-003 requires guard-service `SUPPORTED_CHAINS`, `ChainNativeToken`, the tsconfig package references, `BalanceHandler` `tokensPerIteration`, and CKB commitment/event-trigger extractor registration in `src/jobs/initScanner.ts`. The current Guard configuration pattern also requires `ChainConfigKey`. The cold-storage and balance loops iterate `SUPPORTED_CHAINS`. Create the `@rosen-chains/ckb` and `@rosen-chains/ckb-rpc` packages through the RCS-003 Kodegen flow.

### Cell Selection and Construction

- Select only canonical committed, live Rosen-lock cells absent from in-window candidate, active, and local-pool-spent input sets. Post-check every result.
- For payment and arbitrary construction, first apply H1 with the path's README adapter to the complete depth-qualified identity set. Only when that set admits no valid plan, supplement it with shallow committed Guard-produced change identified from locally persisted CKB transaction rows and apply the same policy again.
- For every supplemented input, fetch its canonical creating transaction and each of that transaction's input-creating transactions through Chain RPC. Require every resolved previous cell to carry the exact configured Rosen hot custody lock.
- For cold balance, triggering, construction, and verification, instead use the complete cold-reachable set. Admit chain-proven shallow Guard outputs without local persistence and exclude shallow user deposits. Add no custody-input depth setting, parent field, or additional identity read.
- Across those paths, xUDT inputs match a registered full type script touched by the payment, arbitrary order, or cold sweep and contain exactly 16 data bytes. Capacity-only inputs have no type and empty data. Never consume DAO, foreign-token, unsupported xUDT, an untouched registered xUDT, other typed cells, immature cellbase outputs, or shallow user-deposit cells.
- Apply exact lock/type/data eligibility throughout each complete paginated identity read. The checked CKB [`get_cells` contract](https://github.com/nervosnetwork/ckb/blob/17d7db5bb423a1b2177e14a132a41d5a91a515f3/rpc/src/module/indexer.rs#L46-L63) matches the secondary script by prefix. Exact secondary-script matching therefore requires the full script as that prefix plus a `script_len_range` bounding it to exactly that length. `[0,1)` selects cells with no type, and output-data filters have exact and length forms.
- Confirm those filters on the deployment release and post-validate every row. Implement the README's `maxIdentityCells`, remaining-budget-plus-one request bound, short-page, advancing-cursor, and over-budget failure rules. Use Chain RPC as selected-input truth.
- Implement the README's complete selector, canonical position and comparators, recursive H1 policy for every automatic path, final input order, and proposal verification. Share comparator and transaction-local output/byte checks between construction and verification. Constructor inventory reads remain local; verification uses only declared inputs. Do not add behavior the README excludes from v1.
- Construct one complete payment with separate xUDT and CKB ledgers. Return `0n` from `getMinimumNativeToken()`. For native CKB, create one recipient whose capacity is exactly the post-fee payment and reject amounts below its actual occupied capacity. For xUDT, create one exact-amount recipient funded at the route's capacity bound and preserve every selected token remainder in one or more same-type H1 custody outputs at exact occupied capacity. Count selected xUDT cells' capacity toward all CKB requirements and never consume a foreign type only for capacity.
- For arbitrary and cold-storage construction, aggregate each full asset identity, process xUDT type groups in ascending packed full-`Script` byte order, take the shortest per-type xUDT-comparator prefix, then add untyped capacity by the native comparator against one shared CKB-capacity ledger. Manual signing supplies exact inputs and performs no selection.
- Use one implementation of the README's recursive eager-cleanup H1 engine for event payments, arbitrary orders, and cold storage. Supply only each path's demand, eligibility, canonical base selector, and service quanta. Event quanta come from the payment, arbitrary quanta from the largest single item per identity, and cold quanta from shared configuration. Canonical minimal composition remains the shared root and unresolved fallback. Do not restate or vary the contract in a chain package; when no permitted form exists, report no-fit through the settled lifecycle.
- Re-finalize canonical deps and the 65-byte lock placeholder after every input or output change. Apply the README's automatic raw-field, dep, header, witness, output, and `outputs_data` constraints without a chain-package variant. Manual intake preserves caller input/output order but enforces the same supported shape. Keep transaction fee and capacity construction separate from route minimum-fee configuration; shortage and no-fit use the settled lifecycle.

### Transaction Verification

#### Transaction-Local Checks

- Override `verifyNoTokenBurned` to ignore native CKB and require exact input/output equality for every registered xUDT full type. Decode each cell amount as unsigned `u128`, accumulate each type group with the same checked `u128` bound as the xUDT script, and reject overflow rather than truncating or constructing an unspendable group. Keep `getTransactionAssets` as raw input/output capacity plus registered-token balances; do not fold fee into a native balance.
- Keep synchronous `verifyTransactionExtraConditions` limited to transaction-local output, witness, route-bound, and signing-status checks. Reject unsupported output types/data and require payment and arbitrary-order xUDT recipient capacity to equal the route bound. Manual prebuilt transactions carry no payment route, so their outputs are checked against the generic supported shapes and occupied-capacity floor instead.
- Implement the [README fee-verification contract](../README.md#transaction-fee-handling) in `verifyTransactionFee`; do not restate its fee definition, capacity-delta, equality, or cap rules here.
- In awaited `verifyPaymentTransaction`, re-resolve every declared input and bind it to the corresponding exact `previous_output`. Require the exact configured Rosen hot lock. Reject DAO, foreign-token, unsupported or non-16-byte xUDT, other typed cells, and untyped non-empty-data custody inputs even when a balanced asset map would hide them.
- Then apply the [README proposal verification](../README.md#custody-concurrency-and-transaction-chaining). Check declared-input eligibility and local nonconflict, comparator and final input order, outputs, conservation, fee, and transaction-type policy.
- For every automatic path, derive `T` from the README's exact packed-Molecule byte domain and validate H1's agreement-visible output counts, service usefulness, pairwise value spread of at most one base unit, and complete transaction-size delta. Derive the base as the complete packed placeholder transaction for the shortest valid declared-input prefix, including its recipient or cold outputs, canonical minimal custody change, deps, and witnesses. Count every extra input and output. Query no constructor inventory and do not reproduce the proposer's cover, repair, cleanup descent, or unresolved state.
- Do not require cold or arbitrary input irreducibility. Payment and arbitrary verification accepts every depth-qualified input without a parent-provenance check and accepts a shallower input only when the Guard-produced-parent predicate passes. Cold H1 checks derive demand from declared cold outputs and shared service quanta; the separate cold-reachable projection may reject a locally unsafe transfer but does not require the proposer to maximize against the verifier's different reservations. A locally visible omitted cell is not by itself grounds for rejection.
- Apply the cold hot-balance projection where applicable, and apply only exact-input and supported-shape checks to manual transactions. This hook is reached on the agreement and verification paths; the manual `/sign` route reaches it only through the CKB branch specified below.

#### Input and Retry Checks

- Treat proposer metadata as untrusted because CKB's transaction hash and canonical SighashAll do not commit resolved input contents. [Bitcoin Runes provides Rosen's re-resolution precedent](https://github.com/rosen-bridge/guard-service/blob/ac5702608e8f441a932b01582881a01be32155b0/packages/chains/bitcoin-runes/lib/bitcoinRunesChain.ts#L1365-L1440).
- For every payment, arbitrary, or manual declared input below the path's configured confirmation depth, independently apply the README's Guard-produced-parent check from canonical Chain RPC. Cold inputs are eligible when depth-qualified or when that same chain-proven parent predicate passes, without requiring local persistence. This is declared-input eligibility, not reproduction of the proposer's unselected set or depth pass.
- Rerun the same current committed-input and common transaction verification immediately before every local CKB TSS submission. A persisted approval or an already generated remote TSS request cannot create a new local share after a shallow input leaves the current canonical chain.
- Define CKB's existing boolean transaction-validity hook so `false` means only canonical input death after the configured grace or another proven permanent raw-transaction fact. Return non-false for input `unknown`, RPC ambiguity, local absence, TSS failure or timeout, wrapper or policy rejection, and unrecognized node errors; that result retains state but does not bypass the complete pre-TSS verification above. Use the same permanence rule for unsigned `signFailed` retry and signed/sent reconciliation. Do not add a shared tri-state API.
- Correct completed-payment synchronization to await the same existing common sequence as ordinary transaction verification: `verifyPaymentTransaction`, `verifyTransactionFee`, and `verifyNoTokenBurned`, followed by synchronous signed `verifyTransactionExtraConditions`, before accepting a response for persistence. Do not create a CKB-only second verifier.
- Use 61 CKB, 142 CKB, and 146 CKB only as exact fixtures for canonical-lock plain CKB, 32-byte-owner-args xUDT, and iCKB respectively. Production capacity always comes from the actual serialized lock, optional type, and data.

### Concurrency and Transaction Paths

#### Agreement and Exclusions

- Extend shared `TxAgreement` and candidate lookup to carry and verify the README-defined immutable placeholder-wrapper `agreementId` only for CKB. Keep every existing chain on its current raw-`txId` agreement path. Keep CKB's ID on the wire and in memory only. Persist through the existing raw-`txId` row, `txJson` wrapper, scalar transaction `type`, and event or order relation; signing must preserve the wrapper's `eventId` and `txType` when it replaces `txJson`. Normalize node JSON only at the network adapter.
- Implement the README's approval rule in the shared acceptance path. A wrapper matching an active row is idempotent only when normalizing the permitted signed lock replacement reconstructs the same placeholder wrapper and `agreementId`. Reject a wrapper whose raw `txId` names a retained invalid row. Every other approval delivered by the shared communicator receives complete current verification and is never rejected merely because its ID is unknown locally. Preserve the communicator's existing behavior and add no CKB-local age or expiry rule.
- Run identity reads, construction, and input re-resolution outside the chain-scoped critical section. Enter the section only for the README's final refresh, selected-input conflict check, and exclusion registration or active-state persistence.
- Key each in-window candidate by recomputed `agreementId` alone. Treat an exact ID match as idempotent retransmission and reject work overlapping any input of a different candidate.
- On approval, atomically remove that candidate and persist active state with its input exclusions before releasing the section. Register a new automatic candidate in memory before release.
- Let candidate exclusions lapse with the existing agreement window and be lost on restart. Persist nothing about a candidate and add no reservation record, tombstone, or deadline-release persistence.
- Retain active state for ambiguous submission and remove its exclusion only through that transaction's authoritative terminal state. Do not use unconfirmed outputs in v1.
- The final sentence above governs every new construction, approval, persistence, manual intake, and TSS decision. It does not require removing exact signed parent and child bytes that CKB re-adds to a local pool after both were detached by a reorg. Treat that as existing transaction reconciliation, never as a source for constructing another successor.

#### Execution State and Conflicts

- Permanent execution outcomes invalidate the existing retained raw-`txId` row. After automatic construction and before agreement, treat a matching invalid row as no-fit under its own diagnostic reason; proposal validation and approval reject it before agreement or TSS, and manual intake rejects it before insertion. Wrapper-level rejection never invalidates that row, and a later request waits until changed construction state produces a different `txId`.
- Reduce signed outcomes to temporary or permanent behavior under the README. Keep the exact node or policy cause as a diagnostic reason, not as an enum that changes persistence behavior.
- Make signing completion a shared atomic compare-and-set: update signed bytes and status only where `txId` matches and current status is `inSign` or `signFailed`. Treat a zero-row result as a discarded late callback. Do not check then update, overwrite `invalid` or `completed`, or add a CKB attempt identifier.
- Keep the invariant local: one Guard never holds overlapping nonterminal active transactions or in-window candidates. Do not claim cross-Guard freedom from conflicting payout construction. When Guards do produce input-conflicting transactions, rely on CKB's single-spend rule: terminalize the loser once canonical input death is authoritative, release its active exclusion, and return its event or order to the existing waiting or retry lifecycle.
- Route every CKB event transaction through the existing shared Guard event-admission path. Do not bypass it with a CKB-specific event owner.
- Treat duplicate-submission error `-1107` only as a successful submission acknowledgement and reannouncement, then reconcile through authoritative `get_transaction`. Do not add an `accepted` lifecycle state, mark the transaction confirmed, or release active inputs from `-1107` alone.

#### Transaction Paths and Manual Intake

- Support Guard's payment, cold-storage, arbitrary-order, and manual prebuilt transaction paths. Apply CKB transaction validation and signing to all four, and apply construction and active-input rules wherever Guard constructs or selects inputs. Payment and arbitrary-order intake reject exact full-script matches for the configured hot and cold custody locks; the dedicated cold-storage path is exempt.
- Implement `extractTransactionOrder` for payment and arbitrary verification exactly as the [README payment-accounting rule](../README.md#payment-accounting) states; do not restate or vary it here. The [fee section](../README.md#transaction-fee-handling) owns cold output shape and amounts, while [custody concurrency](../README.md#custody-concurrency-and-transaction-chaining) owns shared ordering, change, and verification mechanics. Input resolution belongs to transaction verification; do not reuse deposit extraction semantics.
- Event and arbitrary-order callers use the singular transaction wrapper and require exactly one complete payment transaction. Do not split one event's native or xUDT amount across transactions.
- Add no separate transaction input-count cap. The accepted selector, shared transaction-size limit applied to the README's `serializedSizeInBlock`, and shared application cycle ceiling bound construction. Reject readiness when local `tx_pool_info.tx_size_limit` differs from that shared value.
- Reject an empty arbitrary order and any custody-only transaction proposed for it. Route active-input conflict, committed-cell shortage, `identity-read-budget-exceeded`, exhausted-selector no-fit, and retained-invalid-`txId` no-fit through each path's existing waiting or retry lifecycle. Keep each diagnostic reason distinct. Reject intrinsically invalid or unsupported payments.
- Add a CKB-only pre-insert branch to the shared [`/sign` route](https://github.com/rosen-bridge/guard-service/blob/ac5702608e8f441a932b01582881a01be32155b0/services/guard-service/src/api/signTx.ts#L56-L61). That route currently calls only `rawTxToPaymentTransaction` then `DatabaseHandler.insertTx`, so implementing chain verifier hooks does not validate a manual transaction by itself.
- For that branch, parse, verify, and re-resolve every exact input before entering the CKB critical section. Under the section, reject a retained invalid raw `txId`; refresh in-window candidates, active transactions, and local-pool spends; reject any overlap; then insert the validated manual transaction into active state before release.
- Manual intake has no exact-candidate exemption and never treats an overlapping candidate as its own. Leave every existing chain's `/sign` behavior unchanged. Keep parsing and transaction-local checks in the CKB chain package and database and concurrency checks in Guard service.
- Do not add a CKB refund subsystem or describe arbitrary/manual tools as an invalid-deposit recovery service. Keep manual signing disabled by default, preserve Guard's authenticated caller-threshold contract, run CKB's final local conflict check and active-state insertion under the critical section after exact-input validation, and reconcile its active inputs through authoritative submission and terminal state.
